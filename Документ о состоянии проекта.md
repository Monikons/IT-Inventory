 **Отчёт о проделанной работе по проекту «Система учёта инвентаря в компьютерных классах»**

 1\. Что это за проект

Консольное приложение на Python для учёта оборудования компьютерных классов колледжа. Заменяет бумажный журнал и разрозненные таблицы. Каждая единица техники — это карточка с полями:

Обязательные (5):  
\- инвентарный номер (уникальный);  
\- тип (ПК, монитор, принтер и т.д.);  
\- наименование;  
\- кабинет;  
\- состояние (исправно / требует ремонта / списано).

Дополнительные: дата поступления, ответственное лицо.

Пользователи: лаборант (ведёт учёт, ремонт/списание), преподаватель (проверяет оснащение кабинета).

 2\. Текущий статус по спринтам

Проект разбит на 4 спринта по 7 User Stories (US-1…US-7). Фактически реализованы все 7 историй — код inventory.py и main.py закрывает весь CRUD-цикл и сохранение. Тесты написаны под все US.

Таблица: ID \| История \| Спринт по плану \| Статус в коде  
US-1 \| Показать список оборудования \| 1 \| реализовано \+ тесты  
US-2 \| Добавить оборудование \| 2 \| реализовано \+ тесты  
US-3 \| Найти по инв. номеру \| 3 \| реализовано \+ тесты  
US-4 \| Оборудование кабинета \| 3 \| реализовано \+ тесты  
US-5 \| Изменить состояние/кабинет \| 3 \| реализовано \+ тесты  
US-6 \| Удалить запись \| 3 \| реализовано \+ тесты  
US-7 \| Сохранение данных \| 4 \| реализовано \+ тесты

 4\. Как работает код

 4.1 inventory.py — модель и логика

Класс Inventory(filepath=DATA\_FILE):

Константы:  
\- VALID\_STATUSES \= ("исправно", "требует ремонта", "списано");  
\- REQUIRED\_FIELDS \= ("inv\_number", "equipment\_type", "name", "room", "status").

Хранение: JSON-файл. Путь по умолчанию — data/inventory.json.

load() — читает JSON; если файла нет, пустой или он повреждён → пустой список (с печатью предупреждения, без падения).

save() — создаёт директорию при необходимости, пишет JSON с ensure\_ascii=False, indent=2.

CRUD:  
\- list\_all() — возвращает список записей;  
\- find(inv\_number) — поиск по номеру, None если нет;  
\- add(item) → (ok, msg): проверяет непустоту 5 обязательных полей, валидность статуса, уникальность номера; сохраняет;  
\- update(inv\_number, \*\*changes) → (ok, msg): меняет status (с валидацией) и/или room; при отсутствии — «Не найдено»;  
\- delete(inv\_number) → (ok, msg): удаляет, при отсутствии — «Не найдено»;  
\- by\_room(room) — фильтр по кабинету.

Важно: все методы возвращают кортеж (bool, str) — это контракт, на который завязаны тесты (например, msg \== "Не найдено").

 4.2 main.py — консольный интерфейс

\- ANSI-цвета, clear() под Windows/Linux, header(), show\_table(), show\_card(), show\_menu().  
\- Меню: 1 — Показать всё; 2 — Добавить; 3 — Найти по номеру; 4 — Показать кабинет; 5 — Изменить; 6 — Удалить; 0 — Выход.  
\- Действия (action\_\*) обёрнуты в prompt()/msg\_ok()/msg\_err()/msg\_warn(). Пустой ввод в обязательных полях → отмена. Удаление требует подтверждения (да/д/yes/y).  
\- main() импортирует Inventory внутри функции, крутит цикл, ждёт Enter между действиями, выходит через sys.exit(0).

 4.3 test\_inventory.py — тесты (pytest)

Фикстура make\_inv(tmp\_path, items) создаёт временный JSON и Inventory на нём. Набор DEMO — 5 записей. Классы тестов:  
\- TestList — US-1: количество, пустой список, наличие полей;  
\- TestAdd — US-2: валидное добавление, пустое поле, дубликат, невалидный статус;  
\- TestFind — US-3: найден/не найден;  
\- TestByRoom — US-4: найден/пусто;  
\- TestUpdate — US-5: статус, кабинет, не найдено (msg \== "Не найдено"), невалидный статус;  
\- TestDelete — US-6: удаление, не найдено (msg \== "Не найдено");  
\- TestPersistence — US-7: сохранение/перезагрузка, отсутствующий файл, битый JSON.

Запуск: python \-m pytest.

 7\. Известные проблемы и риски

1\. Мусорная запись ffjdj в data/inventory.json — удалить.  
2\. Расхождение README и данных: кабинет INV-0006 (310 vs 3); в DEMO тестов нет INV-0006, хотя в README он есть.  
3\. Спринты «съехали»: код закрывает US-2…US-7, хотя по плану они в спринтах 2–4. Нужно либо переразбить план, либо зафиксировать досрочную реализацию.  
4\. README обещает SQLite («целевое»), но фактически JSON. При передаче стоит явно проговорить, что SQLite ещё не начат.  
5\. update() не валидирует пустой room — пустая строка просто игнорируется (не ошибка, но и не меняет). Это поведение зафиксировано неявно; в US-5 не оговорено.  
6\. add() вызывает .strip() у полей — если в item придёт не строка (например, None), будет AttributeError. Сейчас UI всегда передаёт строки, но при программном вызове это риск.  
7\. load() при повреждённом JSON печатает предупреждение, но не сигнализирует вызывающему коду. Критерий US-7 «не стирает данные молча» выполнен частично: сообщение есть, но программа продолжает с пустым списком.  
8\. Нет .gitignore в переданных файлах — README его упоминает, но среди файлов его нет. Проверить в репозитории.  
9\. Нет папки tests/ в переданном наборе: test\_inventory.py лежит в корне, а README обещает tests/. Либо переместить, либо поправить README/sys.path.  
10\. Цвета ANSI могут не отображаться в некоторых терминалах Windows (старые сборки) — не критично, но для демонстрации стоит проверить на машине QA.

 9\. Краткое резюме для передачи

Проект — консольный учёт инвентаря на Python. Модель (inventory.py) хранит записи в JSON, поддерживает список, добавление с валидацией, поиск, фильтр по кабинету, изменение статуса/кабинета и удаление; все операции возвращают (ok, msg). Реализация фактически опережает план спринтов: закрыты US-1…US-7, хотя по USER\_STORIES они распределены на спринты 1–4. Основные хвосты: мусорная запись ffjdj в данных, рассинхрон README и JSON по INV-0006, отсутствие .gitignore и папки tests/ в переданном наборе, SQLite ещё не начат. Перед демонстрацией — почистить данные, прогнать pytest и пройти протокол US-1 из README.
